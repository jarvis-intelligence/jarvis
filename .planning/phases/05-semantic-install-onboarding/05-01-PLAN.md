<objective>
Make the `semantic` extra discoverable: interactive `jarvis index` offers a one-shot y/N install (`uv pip install --python <sys.executable> jarvis-mcp[semantic]`) once per repo at a TTY, installs on consent and enables semantic search in the same invocation, and remembers a per-repo decline in a new `semantic_declined` registry column — while `jarvis watch`, `jarvis reindex`, MCP paths, and non-TTY runs stay silent and never block on stdin.

Purpose: closes SEMA-01 and SEMA-02, the last two milestone requirements. Users on a base install never learn the extra exists (the only hint today is a skip line after the index already published); this phase turns that moment into an offer, with the index publish itself never delayed or risked.
Output: one additive registry column + setter in `src/jarvis/registry.py`; offer helpers + `_cmd_index` wiring + one argparse default in `src/jarvis/index_cli.py`; 18 new tests across `tests/test_registry.py` and `tests/test_index_cli.py`.

User decisions implemented (05-CONTEXT.md, LOCKED — areas accepted as proposed):
- Area 1 — install mechanics: `uv pip install --python <sys.executable> "jarvis-mcp[semantic]"`; `find_spec` detection on the modules the stage itself imports; install failure = warn + continue, decline NOT remembered; same-invocation enablement after install.
- Area 2 — prompt UX: both-stream isatty gate; placement after publish (never delays the index); prompt `Install semantic search support for this repo? [y/N] ` with Enter = No; EOF/Ctrl-C = decline, remembered, no traceback.
- Area 3 — memory: additive `semantic_declined` column mirroring `fallback_enabled`; cleared only by `jarvis forget` (row death); `--semantic-include` on a declined repo runs as given and does not clear; extra installed → no prompt ever, bit never written.

Research open questions — planner decisions (state per contract):
1. **Reindex offer: NO (index-only).** SEMA-01/SC2 name `jarvis index` literally; `_cmd_reindex` delegates to `_cmd_index` through a synthetic Namespace that deliberately omits `offer_semantic`, so `getattr(args, "offer_semantic", False)` reads False (05-RESEARCH Open Question 1 recommendation adopted). Pinned by test; extending later is a one-line synthetic-Namespace change.
2. **Install spec: UNPINNED, verbatim per lock.** The locked command text is reproduced exactly — `jarvis-mcp[semantic]`, no `==<version>` pin (05-RESEARCH Open Question 2 recommendation adopted). Accepted trade-offs, documented not implemented: a newer PyPI release upgrades jarvis in the venv (affects the next run, never the live process), and a dev consenting inside an unsynced checkout would replace the editable install (05-RESEARCH Pitfall 6 — the offer only fires when the extra is missing, which a synced checkout never is).
3. **uv subprocess timeout: 600 seconds.** Planner discretion per 05-RESEARCH Open Question 3; `subprocess.TimeoutExpired` is caught into the same warn+continue failure path. Unlocked hardening choice, documented here: torch-scale downloads can take minutes, the index is already published so a hang only blocks the offer, and 600s bounds it generously.
</objective>
