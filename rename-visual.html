🗄️ Jarvis Index Survival Guide

What happens to indexed data when you rename a project folder?

Scenario: jarvis index ./epost-ios → rename folder → epost-ios-v2 ❓

✓Quick Answer

The index data is safe. Only one field in the registry goes stale.

✅ Still Valid

  • SCIP index DBkeyed by slug
  • Zoekt search shardkeyed by slug
  • LanceDB semantic tablekeyed by slug
  • Graph (blastRadius)keyed by slug
  • All MCP navigation toolsuse slug only

⚠️ Goes Stale

  • registry.path fieldold abs path
  • jarvis reindex <slug>reads stale path
  • jarvis status <slug>shows old path
💡 One-line takeaway: Index data is keyed by slug, never by folder path. Renaming the folder can't touch it. Re-run jarvis index <new-path> --slug epost-ios to repair the one stale field.

1Before the rename — everything wired

When you run jarvis index ./epost-ios with no --slug, the slug is derived from the folder name.

The index only knows the slug. It never reads the folder path at query time — so all MCP tools keep working when you pass repo="epost-ios".

3What works vs. what breaks

MCP query tools resolve by slug only and stay fully functional. CLI commands that read the registry's stored path are affected.

✅ MCP Tools (slug only)

  • documentSymbolsworks
  • goToDefinitionworks
  • findReferencesworks
  • callHierarchyworks
  • typeHierarchyworks
  • searchCodeworks
  • semanticSearchworks
  • blastRadiusworks

⚠️ CLI Commands

  • jarvis status epost-iosstale path
  • jarvis reindex epost-iosFAILS
  • jarvis index <new> (no --slug)creates duplicate

Why reindex breaks — the one weak link

jarvis reindex epost-ios
_cmd_reindex() looks up the slug in the registry
repo = registry.get("epost-ios")
reads the stored path field → "/Users/.../epost-ios"
index_repo(path=repo.path)
hands the stale path to the indexing pipeline
_git_head("/Users/.../epost-ios")
❌ folder doesn't exist → fatal: cannot change to...

4The fix — re-index under the old slug

Pass the new folder path but keep the old slug. The registry's ON CONFLICT(slug) DO UPDATE rewrites the stale path field, and the atomic publish rebuilds the index in place.

$ jarvis index /path/to/epost-ios-v2 --slug epost-ios
index_repo(path=/path/epost-ios-v2, slug="epost-ios")
new path + old slug → registry upsert
ON CONFLICT(slug) DO UPDATE SET path=excluded.path
✅ path field rewritten to the new location
_publish_atomically()
writes index-xyz.db, then flips the current pointer
~/.jarvis/scip/_/epost-ios/_/
old index-abc.db replaced → new index-xyz.db live
✅ Result: Same slug epost-ios, corrected path, rebuilt index. No orphaned data, no duplicate slugs, all tools continue to work with repo="epost-ios".

⚠️ Don't do this: jarvis index /path/to/epost-ios-v2 (no --slug) creates a brand-new slug epost-ios-v2, orphaning the old epost-ios index, Zoekt shard, and LanceDB table on disk.
